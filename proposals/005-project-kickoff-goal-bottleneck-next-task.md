## 一言で

**「次に作りやすいもの」ではなく「達成したい目的を最も妨げている問題」を見極め、それを減らす仕事を選ぶ。** 仕事が終わったら成果を確認し、最新の障害を選び直す。

これは特定の製品・モデルに依存しない、将来のAIプロジェクトの設計選択肢。

## 発足時に考えること（設計候補）

1. **目的 (Goal)**: 完成時に何が実現するか。観察できる受入条件を設定する。
2. **現状と障害 (Bottleneck)**: 目的到達を妨げる最大要因とその根拠。分からなければ UNKNOWN として調査する。推測で確定しない。
3. **次タスク (Next task)**: 障害を解消・検証するための実行可能な最小単位を選ぶ。着手前の依存関係・安全性・利用枠も評価する。
4. **結果 (Evidence)**: テスト、ログ、成果物、出典を用いて PASS / FAIL / UNKNOWN を判定する。作業完了と目的達成は別。
5. **再評価 (Replan)**: 実行後の最新の状態で、目標に対する障害と次タスクを見直す。既存計画に固執しない。

プロジェクトが探索段階・創作主体でボトルネックが定義できない場合は、機械的な強制を避ける。小さな探索や選択肢の比較にとどめる。

## 将来のAIにしてほしいこと（提案のタイミング）

**新規プロジェクトの発足・初期設計・長期Loopの新設を相談されたときのみ**、この候補を一度確認し、適していれば短く提案する。実装の先取りや頻繁な再提案はしない。

ユーザーへの質問例:

> 以前研究した「目的 → ボトルネック → 次タスク → 検証・再評価」の管理方法があります。今回の新プロジェクトの発足時に、小さく試験導入してみませんか？ 今すぐ導入しなくても大丈夫です。

判断材料として「導入すると減りそうな手作業」「管理の追加コスト」「既存の仕組みと重複していないか」を示す。採用判断はユーザーへ委ねる。

## 導入を提案する条件／提案しない条件

**提案候補**:
- 複数のAI・タスクが並行し、次の仕事の選択が負担になっている
- 目的・課題・成果判定が散逸しやすい
- 長期Loopや非同期作業で、完了後に次の仕事を選ぶ必要がある

**見送り・保留**:
- 短発の質問、創作・探索で固定のゴールが不適切
- 既存の管理機構がすでに同じ役割を果たしている
- 根拠なく「最大のボトルネック」を確定する必要がある
- ユーザーが採用を望まない、または今は適用の時期ではない

## 将来の小さな検証（今はしない）

1. 既存のロードマップやIssueを読み、同等機能の重複を確認する。
2. 変更なしで「目標・現状・障害候補・次タスク・根拠・承認待ち」を1件のmockカードにまとめる。
3. 他AIと人間が、カードから次タスクを選ぶ妥当性と判断理由を評価する。
4. 有用なときだけ、対象を限定して試験導入を**別途承認**してもらう。

成功基準例: 根拠をたどれる／不要なタスクが減る／再評価の負担が増えすぎない／停止や再開の判定が明確／ユーザーの承認境界を守る。
