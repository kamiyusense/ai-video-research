## 一言で
**新しいAIを全部覚えるより、まだ解決できない実際の困りごとを集めておく。新機能に出会った時、過去の困りごとを解けるか照らし合わせ、価値があれば人間に提案する。**

これは「課題ドリブン／未解決課題のストック法」というアイデア。研究室の学びを行動につなげる候補であって、強制ルールではない。

## 「目的→障害→次タスク管理」P005との関係
- **P005**: いま進めている特定プロジェクトの目標に対し、次に着手する障害と仕事を選ぶ。
- **P006**: 今は実現が難しい課題・アイデアを**複数のプロジェクトや時間にまたがって保管**し、将来の技術と再照合する。
- 相互補完は可能だが、別々の管理課題。P005が未採用でもP006は単独で利用できる。
- いずれも既存Loopへの即時適用を求めない。

## 課題カードの最小形式（将来使う場合）
| フィールド | 意味 |
|---|---|
| task_id | 重複しない課題ID |
| 困っていること | 人間の言葉で1〜2行 |
| できるようになりたいこと | 成功の判断基準 |
| 過去に試した方法 | わかる範囲。未実施ならNOT_RUN |
| 詰まった理由と証拠 | 未確認ならUNKNOWN |
| 制約 | 料金、権限、保存先、プラン、端末、作業時間など |
| 保留理由 | 今は無理／費用が高い／手間が大きい／優先度低い等 |
| 再評価候補 | 関係のある機能・技術名。未確定なら空欄 |
| 最終確認日／状態 | OPEN / PARKED / TESTABLE / SOLVED / REJECTED / UNKNOWN |

**課題を保存しただけで外部へ送信したり、勝手に再実行したりしない。**

## AIに期待する将来の振る舞い（実装前の提案）
1. ユーザーが新AI・機能について調べている／新しいプロジェクトを企画している場面で、許可範囲の課題一覧を参照する。
2. 新機能の**実際の公式仕様**を確認し、どの保留課題の障害を解消できそうか根拠と合わせて示す。
3. 使える根拠がある場合だけ、「以前できなかった〇〇、今の機能なら試せそうです。小さな検証をしませんか？」と提案する。
4. 実装・課金・権限変更・外部モデル起動等は、別途承認を得てから進める。
5. 失敗・未対応なら、解決したと偽らず保留のまま証拠を更新する。何度も同じ提案を押し付けない。

## 適用例（実際の運用を開始するものではない）
- 長尺のYouTube解析がブラウザでフリーズする → 新しい動画入力・映像切出し・保存機能が登場した時に再検討。
- 一時チャットで調査結果が失われる → 保存・逐次回収・軽量出力の選択肢を見直す。
- 反復するPC操作を毎回AIに画面認識させている → 公式APIやスクリプト化が可能になったときに小規模mockを検討。

## 実施前に確認すること
- AIに課題を見つけさせるだけなら、メモ・GitHub Issue・ノートなど既存の道具を活用できないか。
- 保存先・所有者・内容へのアクセス権と、何がAIへ送信されるか。
- 古い課題の現行性。既に解決したものに同じ修正を提案しないこと。
- 現実に削減できる人間の操作時間が、管理コストより大きいか。
- 定期巡回の費用・イベント枠・起動権限等。**現時点では自動巡回を設定しない**。

## 将来の小さい検証候補（今はNOT_RUN）
1. 公開情報だけで扱える架空の課題3件と新機能1件でmockを作る。
2. AIに「適用可／条件付き／不可／UNKNOWN」を分類させ、根拠URLを付けさせる。
3. 人間の判断と比較して誤提案・重複提案を計測する。
4. ユーザーに採用を相談する。採用しない場合はそこで停止。

受入条件: 課題IDと証拠の追跡、解決済みへの再提案防止、UNKNOWN維持、課金・書込み・LIVE等の無断実行なし。
