# OKF参考ノート作成Skill（試作 v0.1）

目的：動画以外の参考資料（記事・ポスト・ノート・スライド・README など）を、動画の研究ノートと**同じ荷札の形**で、**リンク付き・出どころの確かさ付き**で保管できる形にする。あとからAIが検索しやすく、人が読んでも出どころが分かることが大事。

このSkillは**文章を作るだけ**。GitHub・Drive・NotebookLMへの保存、ファイルの削除・上書きは、指示されない限りしない。作った結果は、1ファイル＝1つのコードブロックで返す。

## 0-a. 保存量の方針（オーナー決定 2026-10-30）

- **要約だけを保存する。原文の全文は保存しない。** 同じ内容を原文と要約で2回書いても、探せる内容は変わらず、参照する量が増えるだけだから。
- 長い資料（GitHubのREADME、長い記事など）は、**要約＋元のURL**だけにする。要約は300字以内＋項目の一覧まで。手順・コマンドの全文は書かない（必要ならURLで見に行く）。
- そのかわり、**検索に効く荷札を充実させる**：`keywords`（固有名詞・ツール名・別名・日本語と英語の両方）、`tags`、`description`（何の資料で何が分かるか）。検索で見つかることが目的。
- 本文の見出しは短くしてよい（「独自要約」「項目」「限界・未確認」だけでも可）。ただし「限界・未確認」は必ず書く。

## 0. 守ること（最優先）

1. **読めなかったものは「読めなかった」と書く。** 推測で中身を埋めない。ログイン・有料壁・取得エラー（例：Xの本文がHTTP 402）で読めない時は `content_status: "NOT_READ"`。他のAIの要約（Grokのレポートなど）しか手元に無い時は `source_tier: "SECONDARY_SUMMARY"`、`content_status: "SUMMARY_ONLY"`。
2. **数字・固有名詞は、原文にあるものだけ。** 要約の数字は「要約の写し・未照合」と書く。「最大◯%」「◯万人」のような宣伝の数字は、宣伝側の主張として扱う。
3. **URLは、元のまま全部残す。** 壊れたURL（IDの末尾に余計な文字など）は、直したURLと、直した事実の両方を書く。重複するURLは1件にまとめて、まとめたことを書く。
4. **出どころを混ぜない。** 一次情報（原文を自分で読めた）と二次情報（他人／他AIの要約）を、荷札で分ける。
5. **個人名・鍵・パスワード・非公開の内容は書かない。** オーナーの呼び名は「オーナー」。
6. **既存ファイルは上書きしない。** 同じ `logical_id` が既にあると分かっている時は、新しいファイル名（`_2`）にして、重複の可能性を書く。

## 1. 入力の種類（source_kind）

- `x_post_collection`：Xのポストのまとめ（本文が読めない時が多い）
- `x_post`：Xのポスト1件
- `article`：Web記事・ブログ
- `google_slides` / `google_doc`：スライド・ドキュメント
- `github_readme` / `github_repo`：GitHub
- `shared_file`：人がまとめたファイル（Markdown・PDF・メモ）
- `note`：オーナー自身のメモ

## 2. 荷札（YAML）の形

```yaml
---
okf_version: "0.2"
type: "REFERENCE_NOTE"
title: "参考ノート：<30字ほどの題>"
description: "<200字以内。何の資料で、何が分かるか。出どころの確かさも一言>"
tags:
  - "AI技術研究室"
  - "参考資料"
  - "<主題のタグ 1〜3個>"
keywords:               # 検索用。固有名詞・ツール名・別名・日英両方。5〜15個
  - "<キーワード>"
logical_id: "ref:<source_kind>:<日付またはID>:<短い英数字名>"
source_kind: "<上の種類>"
source_tier: "PRIMARY | SECONDARY_SUMMARY"
source_made_by: "<二次情報なら作った人／AI。一次なら省略>"
content_status: "READ | READ_VIA_TOOL_SUMMARY | SUMMARY_ONLY | NOT_READ"
acquired_at: "YYYY-MM-DD"
acquisition_method: "<どうやって手に入れたか。例：公開ページを取得ツールで読んだ／オーナーが貼った>"
resource: "<元のURL。無ければ UNKNOWN>"
canonical_url: "<正規化したURL。無ければ UNKNOWN>"
published_at: "YYYY-MM-DD（分かる時だけ）"
related_records:        # 関係が確かなものだけ。無ければ書かない
  - target_id: "<相手の logical_id>"
    relation: "COMPLEMENTS | EXTENDS | CONTRADICTS | DERIVED_FROM"
    note: "<関係の説明>"
---
```

- `logical_id` は後から変えない（検索の鍵になる）。
- YAMLの値に「:」や引用符が入る時は、必ず全体を二重引用符で囲む。

## 3. 本文の形（この順番）

1. `# <題>`
2. `## 独自要約`（300字以内）
3. `## 項目` または `## 内容の流れ`（資料が複数の項目なら、1項目＝1行＋リンク。動画なら `&t=<秒>s` つきのURL）
4. `## 重要な知見`（箇条書き。根拠が資料のどこかを添える）
5. `## この研究室への応用`（AI動画研究室・ループ・Skillにどう使えるか。3つまで）
6. `## 限界・未確認`（読めなかった所・未照合の数字・出どころの弱さ。必ず書く）

## 4. 手順

1. 資料を読む。読めない所を先に洗い出す（本文・ログイン・有料壁・外国語）。
2. 一次か二次かを決める。
3. `logical_id` を決める（例：`ref:github:morluto-rea:readme-ja`）。
4. 荷札→本文の順で書く。本文は上の6見出しを守る。
5. 最後に自己点検（次の節）をして、不足を直してから返す。

## 5. 返す前の自己点検（全部「はい」で返す）

- [ ] 読めなかった所を「限界・未確認」に書いたか
- [ ] 数字・固有名詞は原文か、要約の写し（未照合）と書いてあるか
- [ ] URLは元のまま残し、直した所は直した旨を書いたか
- [ ] 一次情報と二次情報を `source_tier` で分けたか
- [ ] 個人名・鍵・非公開の内容を入れていないか
- [ ] `logical_id` は他と重複していないか（分からなければ「重複確認未実施」と書く）
- [ ] 1ファイル＝1コードブロックで返したか

## 6. Grokで使うとき

- 本文が読める場合は一次情報として扱う。読めない場合は「読めなかった」と書き、Claude側で別途取得・照合する余地を `限界・未確認` に残す。
- Xの記事・ポストの本文は、Grokなら読めることが多い。その時は `acquisition_method` に「Grokが読んだ」と書く。
- 出力は、ClaudeがそのままOKFファイルとして受け取れるよう、ファイル名の見出し＋コードブロックの形にする。

## 7. ファイル名

`ref-<source_kind>-<日付>-<連番または短い名前>.md`（例：`ref-x-bookmarks-2026-10-29-01-agent-design.md`）

## 8. 保存について（このSkillでは行わない）

保存先（GitHubのどこか、NotebookLMに入れるか）は、オーナーの指示と、別の決まり（保管ルール）で決める。このSkillは、保存前の「整った下書き」を返すところまで。
