## 最優先｜1動画2ソースMVP完成契約（2026-10-19再確定）

**本節は旧来の暫定「YouTube URLソース＋研究ノートで実用成功」より優先する。新規動画の取り込みでは、YouTube URLソースを登録せず（R2・オプトイン無し）「字幕原文OKF ＋ 研究ノートOKF」の純粋2ソース登録を絶対の原則とする。複数Notebookの横断検索、ChatGPTからのNotebook直接参照、1動画1ソース最適化、Notebook間の分散配置は今回は保留。** 既存LIVE試験でURL＋研究ノートが通っても、正式な2ソースOKF完成としては `PARTIAL` と判定する。既存の成功済み工程・登録物を消したり重複登録したりしない。特に、過去に登録済みのYouTube URLソースや研究カード、総合索引などの既存資料は勝手に削除・消去せず、そのまま非破壊で保持・保護する（例外：YouTube URLソースは、同じ動画の字幕原文OKFを登録・読み戻し確認した後に限り削除してよい＝2026-10-20 相棒決定）。

**Notebookの必須2ソース（新規動画は1動画につき純粋2ソース登録を原則とする）**:

1. **原文OKFソース** `youtube:<video_id>:transcript`。許諾・利用条件の範囲で取得した字幕原文の**取得できた全量**を独立資料にする。荷札（OKF v0.2の既存契約に合わせたYAMLフロントマター）に資料種別、タイトル、`video_id`、**元YouTube URL**、**動画の投稿日時 `published_at`（R4）**、言語、取得元/方法、取得範囲、取得時刻、cue数、完全性/照合状態、相手の研究資料IDを記す。**本文は時刻なしを正とし（R3）、cueの発話テキストを連結して段落に分ける**。読みやすい章・段落索引を加えてよいが、**発話テキスト自体は改変・清書・補完しない**。誤変換の修正候補や注釈は原文と明確に分ける。字幕の一部のみを取得した場合は `UNVERIFIED` / `PARTIAL` を明記し、欠けた箇所を創作しない。入力・生成経路で先頭400 cue等に黙って切り詰めず、取得全量/研究に実際に使った範囲を区別する。
2. **研究ノートOKFソース** `youtube:<video_id>:research`。**元YouTube URL**と**投稿日時 `published_at`**を同様に持ち、根拠時刻は時刻つきURLで示す。独自の日本語要約、分かりやすい技術解説、確認済み時刻、公式照合、限界/UNKNOWN、活用案、字幕根拠への参照をOKF荷札＋見出しで整理する。既存のGitHub研究ノートを正式な独自研究正本として再利用し、Notebook側はAI参照用のコピーとする。原文からの引用とAI解釈を混同しない。

**最低必須の相互リンク**: 両資料に相手の `logical_id`（`:transcript` ↔ `:research`）、元動画URL、判明した場合のみNotebook固有ソースIDまたは実際に開けるリンクを記録する。存在を確認していない架空のNotebook URL・リンクを生成しない。GitHubに保存する研究ノート側でも原文の論理IDを保持する。両資料が別ソースとして存在し、相互参照が解決または明確に`UNKNOWN`と識別されることを検証する。

**関連話題へのリンクは次点（4大意味付き関係ラベル）**: 既存RAG研究 `pRfC1DILDEM` とOKF研究 `u3ka_AAb8qE` を基準例に、意味付き関連を検索可能にする。関係ラベルは以下の4分類を厳格に使い分ける：
- **`COMPLEMENTS`（相互補完）**: 異なるアプローチ・視点・レイヤーから同一の目的を補い合い、組み合わせで完全な解決策・全体像を成す関係（基準例: OKFの書類構造化 ↔ RAGの質問振り分け探索）。
- **`EXTENDS`（発展・拡張）**: 先行研究の概念・技術を基礎として引き継ぎ、より高度・広範な領域へ発展・深化させている関係（例: 基本エージェント ↔ マルチエージェント合議・自己改善ループ）。
- **`UPDATES`（更新・改定）**: 先行研究の仕様変更、新バージョン、非推奨化、あるいは前提条件の更新を伝えている関係（例: 旧API/モデル仕様 ↔ 新機能・新ベンチマークでの追試）。
- **`CONTRADICTS`（矛盾・対立）**: 同一課題に対して相反する主張・結論・ベンチマーク結果・設計哲学が対立している関係（例: 全件事前ベクトルインデックス推奨 ↔ オンデマンドgrep探索推奨）。
候補 `CANDIDATE` と確認済み `CONFIRMED` を分け、関連理由と根拠を保存し、リンク先実在・GitHub相対パス・可能な逆リンクを検証する。名前やタグが似ているだけで確定させない。リンク先未確認は `UNKNOWN` / `UNRESOLVED`。
- **関連理由と出典の保存義務**: 関連レコード（`related_records`）には、なぜその関係であるかの**具体的な関連理由（`note`）**と、動画内の該当時刻・章・発言箇所・公式URLなどの**明確な出典・一次根拠（`evidence`）**の双方を必ず保存する。出典不明のまま関係を捏造・保存してはならず、未確認時は明示的に `UNKNOWN` と記録する。
- **Notebook側の逆リンク（R6の設計案）**: NotebookLMは登録済みソースの本文を書き換えられないため、古い研究ノートに逆リンクを足せない。逆リンクは**「関連索引OKF」1ソース**（全動画の関係一覧。A→B と B→A の両方向、`status`・`note`・`evidence`・各ノートの `published_at` つき）にまとめ、関係が増えたら新版を登録→読み戻し一致→旧版を削除する形で**この1ソースだけを差し替える**（差し替えは削除を含むため、実行は相棒の承認後）。GitHub側は各研究ノートの `related_records` が正本。
- **R6のリスクと対策**: (1) 誤リンク：自動推定は `CANDIDATE` 止まりにし、`CONFIRMED` には根拠の読み戻しを必須にする。(2) 古い情報の混入：`published_at` を索引にも載せ、新しい動画が古い主張を改める関係は `UPDATES` で示す（回答では新しい方を優先し、古い方は「当時の情報」と区別）。(3) 索引の差し替え失敗：新版の読み戻し一致を確認するまで旧版を消さない。

**保存先・権利境界**: 字幕全文・動画本体・長い転載をGitHubに保存しない。独立字幕ソースをNotebookへ複製する権利/利用規約が確認できない場合は、無断複製せず `BLOCKED_RIGHTS_OR_TERMS` / `UNKNOWN` と記録する。許可された保存先以外へ送信しない。GitHubには独自研究、URL、索引、関係ID、NotebookソースID、取得/照合状況、短い独自説明を保存する。契約違反を「成功」と報告しない。

**完成判定（新SUCCESS条件：2-Source OKF完全成功基準）**: `SUCCESS_2_SOURCE_OKF` は、以下の全条件を満たした場合のみ確定する：(1) 新規動画における純粋2ソース登録（字幕原文OKF ＋ 研究ノートOKF、YouTube URLソースは登録しない）、(1-2) 両資料に `published_at`（R4）と動画URLがあること、(2) 事後読み戻し（Post-readback）により実画面DOM上で**別々の独立した2つのNotebookソース項目（`Index_note != Index_transcript`）として個別に立証**されること（単一要素の二重カウントによる誤認を排除）、(3) 双方のメタデータに記載された動画ID、元YouTube URLが一致し、相手の論理ID（`:transcript` ↔ `:research`）を相互参照していること、(4) 字幕全文（時刻なし・段落化）が要約・改変・創作なく保存され、研究ノートの時刻リンクは確認済みの時刻だけであること、(5) GitHub研究成果と索引の非defaultブランチ保存/readbackおよび自然言語QA検証が通過していること。**Driveへのファイル配置のみ、Chrome/Notebookタブ検出のみ、同一ソースの二重カウントのみ、Mock結果のみをもってPASSにしてはならない（偽PASS判定の完全禁止）**。単なるYouTube URL＋研究ノート、Drive上への配置、CDPタブ検出、Mock、ソース件数のみでは不可。Notebook保存済みであっても字幕原文の全文完全性未証明なら `UNVERIFIED` を保ち、**取得できた字幕全量の保存**と**動画全体の字幕完全性の証明**は別判定とする。保存不可・未確認の項目があれば `PARTIAL` / `BLOCKED` / `UNKNOWN` とし、現行パイプラインの旧 `SUCCESS` は2ソースOKF完成PASSへ読み替えない。

**運用の境界（重複回避と不足ソース差分追加）**: URL入力だけでこの2ソースを作ることを目標とする。同一動画について登録済みのソース（YouTube URL、研究ノートOKF、字幕原文OKF等）がある場合は、事前読み戻し（Pre-readback）で確認し、重複登録を避けて**不足しているソースのみをピンポイントで差分追加**する（全ソース登録済み時は安全停止・No-Op）。すでにGitHub保存・Notebookソース追加を済ませた動画には安全な再開/不足分だけの追加を使い、成功済みのGemini LIVE・GitHub Pushを再実行しない。外部モデルLIVE、Notebook/Drive/GASへの新規LIVE書き込みは対象を明示した承認を要する。許可済みの非defaultブランチにおける設計・静的/Mock検証は先行してよい。

**Notebook枠の扱い（今回のスコープ外）**: 1ノート300ソースのユーザー環境では2ソース/動画のため最大150動画相当（既存ソースがある場合は残枠分のみ）。複数Notebookの自動配分・横断照会、ChatGPTからNotebookへの直接接続は**保留**とする。GitHub研究ノートのNotebook省略方式は冒頭R1-Bの条件（相互参照の実証＋相棒承認）を満たすまで採用せず、今回のMVP実装を拡張しない。

## 0. 目的・非交渉のユーザー要件

目的は動画要約の本数を増やすことではない。**元資料を保護し、独自研究をOKFで体系化し、関連研究を結び、AIが質問の種類に応じて根拠付きで回答できる継続研究室**にすること。

1. **先頭に荷札**: 各資料に資料種別、タイトル、動画ID、元URL、取得日・方法、言語、検証状態等のメタデータを付ける。OKF v0.2準拠を目標とする。必須項目・拡張項目・現在の公式仕様はPhase 1で独立照合する。
2. **1件1ファイル**: 少なくとも「字幕原文」と「研究成果」を別々の資料として扱う。YouTube URLソースがあるだけで独立した字幕原文ファイルを作成・全文検証済みとは見なさない。
3. **原文は改変しない**: 取得した字幕を独立したNotebookソースとして可能な限りそのまま保持し、ASR誤変換、取得欠落、原文一致の未確認は明記する。修正候補・意味補足・要約・技術説明は研究ノート側へ記載。取得していない原文を推測生成しない。
4. **関係をリンクで結ぶ**: 字幕原文⇔研究ノート、関連動画⇔関連動画、研究成果⇔公式資料・未解決課題を結ぶ。存在するリンクの解決、意味付け・根拠、重複の検査を行う。
5. **今後の新着にも同じルール**: 最初の2動画だけの一回限りの整理ではなく、Gemini Taskの入口から保存・読み戻しまで組み込む。
6. **人間の手間を増やさない**: 既存のGemini→NotebookおよびGemini→Drive→GAS→GitHub経路を活かし、静的/Mockと実機を混同せず段階的に省力化する。
7. **質問回答で使えること**: 登録数、時系列、全体傾向、元発言確認を同一の曖昧なRAG処理に任せない。質問に合う処理を選び、証拠まで戻れるようにする。

## 2. 文書モデル（設計目標）

1動画に**最低2つの独立したOKF論理資料（Notebookでも別ソース）**:
- `youtube:<video_id>:transcript`: 原字幕テキストを保持するNotebook独立ソース（原文を改変しない）。可能ならOKF荷札。動画URL、言語、取得方法、取得範囲、完全性検証状況、関連研究ID、Notebook実ソースIDを管理。
- `youtube:<video_id>:research`: Geminiが作ったOKF研究ノート。要約、詳細技術解説、章立てと確かな時刻根拠、公式照合、主張と原文の該当箇所、関連研究、UNKNOWN事項を保持。NotebookとGitHubに別経路で保存。

YouTube URLソースは新規登録しない（R2）。過去に登録済みのURLソースは **別のURLソース** として管理し、2独立資料に含めて数えない。Notebookでの「ファイル」「ソース」「ページ」の実装差は確認対象。GitHubの研究パスやNotebook固有ソースIDは、研究室の論理IDと混同しない。

荷札項目の候補（`published_at` は必須・R4）: `type` / `title` / `video_id` / `resource` / `published_at` / `language` / `acquired_at` / `acquisition_method` / `verification_status` / `tags` / `sources` / `related_records`。どれがOKF正式項目でどれが研究室独自拡張かをPhase 1で明文化する。

**原文改変禁止の境界**: 荷札や識別可能な段落IDは原文の外側に付ける。原文の誤字修正、正規化、要約、注釈、語句の統一は原文本文に混ぜず研究ノートまたは派生索引へ。段落・動画時刻リンクは一次根拠がある箇所だけ。

**関連情報**: 既存の `related_records` を再利用する（`COMPLEMENTS`, `EXTENDS`, `UPDATES`, `CONTRADICTS`, `RESOLVES_BACKLOG`）。`target_id`、関係理由、出典/確認状態、リンク先存在確認、逆リンク・索引更新方針を保持。似た単語だけで関連確定しない。存在しない宛先は `UNRESOLVED` / `UNKNOWN` として実リンクと分離。Markdown相対リンクはGitHubでは利用可能、Notebookが自動横断解決できるかはUNKNOWN。Notebook用には安定動画ID・ソース識別子を併記。

**目次と更新**: OKFの `index.md` / `log.md` 相当を定義し、既存 `registry.json`、`loop_state.json`、`automation/gemini-notebook/state/` と責務を整理。重複した「唯一の正本」を増やさない。
